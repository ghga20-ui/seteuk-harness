그리고 첫 화면은 4단계 중 3단계를 `hidden`으로 감춰, "화면 자체가 순서"라는 설계 원칙 5를 코드가 정면으로 부정한다.

## 1. 잘 된 점 (다음 단계에서 반드시 지킬 것) — 6개

**G1. 크림·베이지 함정을 실제로 피했다.**
`--bg: #fbfbfa` → OKLCH **L=0.988, C=0.0013, H=106.4**. 금지 대역(L 0.84–0.97, C<0.06, hue 40–100)의 **L 상한 위**이고 채도는 사실상 0이다. 토큰명도 `--paper/--cream/--sand/--ivory`가 아니라 `--bg/--card/--src`다. 2026년 AI 기본값을 우연이 아니라 정확히 비껴갔다. **이 세 줄은 건드리지 마라.**

**G2. 절대 금지 목록 3종을 실제로 위반하지 않았다.**
- 사이드 스트라이프 없음 — `.card.flag { border-color: var(--warn); }`는 **전체 테두리 색 교체**다. 가장 흔히 무너지는 지점을 옳게 처리했다.
- `background-clip: text` 0건, 그라데이션 0건, `backdrop-filter` 0건.
- 히어로 지표 템플릿 없음. 큰 숫자가 화면을 지배하지 않는다.

**G3. 실명 경계가 UI 문구로 드러나 있다.**
`.privacy` 블록이 "**명렬.json·점수원본.json·검수본.json에는 실명이 들어 있으므로 AI에게 주지 마십시오 — AI에게 줄 것은 `검수diff.json`뿐입니다**"를 명시한다. 설계 원칙 3이 코드에 실제로 반영된 드문 경우다. `buildOutputs()`의 diff에 `학번`·`이름`이 실제로 빠져 있는 것까지 일치한다.

**G4. "왜 이렇게 했는가"가 코드 주석으로 남아 있다.**
`bannedHits()` 위 주석 — "*금지문자패턴은 정규식이다 … 실제로 그렇게 새어 있었다*", `parseScores()` 위 — "*단순히 '값이 많이 찬 열'로 고르면 이름 열을 점수로 읽어 버린다*". 실패 사례가 주석으로 보존돼 있다. 리디자인 때 이 주석들을 잃지 마라.

**G5. 열 판별 결과를 사람 말로 되돌려준다.**
`열 판별: 값 판별 — 1번째 열을 학번, 2번째 열을 이름으로 읽었습니다.` 기계가 뭘 했는지 교사가 검증할 수 있는 형태로 노출한다. 설계 원칙 1(판단이 필요한 곳에서 멈춘다)의 올바른 구현.

**G6. 네이티브 컨트롤을 재발명하지 않았다.**
체크박스는 `accent-color: var(--accent)`를 쓴 진짜 `<input type=checkbox>`이고, 커스텀 스크롤바·커스텀 셀렉트가 없다. product 레지스터의 "표준 어포던스 재발명 금지"를 지켰다.

## 2. 색 · 대비 (실측)

### P0-1 · 다크 모드 주 버튼 글자가 읽히지 않는다 — **2.26:1**
```css
button.primary { background: var(--accent); border-color: var(--accent); color: #fff; font-weight: 600; }
/* dark: --accent: #7fb99a */
```
| | 값 | 판정 |
|---|---|---|
| 라이트 `#fff` on `#2f6f4e` | **5.99:1** | 통과 |
| 다크 `#fff` on `#7fb99a` | **2.26:1** | **위반** (본문 4.5 / 큰 글씨 3 둘 다 미달) |

`.9rem`(14.4px) `font-weight:600` → 큰 글씨 기준(18.66px bold)에도 못 미친다. 해당 요소는 `#save`(명렬 저장)와 `#rv-save`(검수본 저장) — **파이프라인의 두 개 종결 동작 전부**다. 다크 모드 노트북이 1급 시민이라면 이건 P0다.
→ 조치: 다크에서 주 버튼은 `color: #16171a`(어두운 글자 on 밝은 accent, 약 8:1) 또는 accent를 어둡게 하고 흰 글자 유지 중 택1. 두 테마가 같은 토큰으로 반대 결과를 내는 구조 자체를 고쳐야 한다.

### P0-2 · 중복 학번 행이 사실상 보이지 않는다 — 다크 **1.006:1**
```css
tr.dup td { background: var(--badbg); }
```
| | 행 배경 vs 카드 | 판정 |
|---|---|---|
| 라이트 `#fdeeeb` vs `#fff` | **1.129:1** | 형광등 아래 저가 모니터에서 거의 안 보임 |
| 다크 `#2b1c19` vs `#1e1f23` | **1.006:1** | **완전히 동일하게 보임** |

게다가 **색만이 유일한 표시**다. 행 안에 "중복" 같은 글자가 없다. `PRODUCT.md` 접근성 조항 "색만으로 상태를 전달하지 않는다"와 설계 원칙 2 "조용한 실패를 시각화한다"를 **동시에** 위반한다. 실측에서 63%가 오류 없이 틀렸다고 적어 놓은 그 실패가, 바로 이 행이다.
→ 조치: 행에 텍스트 배지(`중복`)와 3:1 이상 테두리/왼쪽 아닌 전체 강조. 배경 틴트는 보조로만.

### P0-3 · "경고 0건"을 안전으로 읽히게 두고 있다
```js
document.getElementById("stats").innerHTML = [
  ["", `${students.length}명`],
  [dup ? "bad" : "", `중복 ${dup}`],
  [blank ? "warn" : "", `빈칸 ${blank}`],
]
```
`dup === 0`이면 클래스가 빈 문자열 → `.chip` 기본 배경 `var(--okbg)` = **연녹색(성공색)**. 즉 `중복 0`이 초록 알약으로 렌더된다. 설계 원칙 2가 명시적으로 금지한 것을 정확히 하고 있다. 게다가 중립 정보인 `40명`도 같은 초록을 입는다 — 성공색이 의미 없이 소비된다.
→ 조치: 0은 초록이 아니라 중립(테두리만)으로. 검사가 **수행됐다**는 사실과 **결과가 0**이라는 사실을 분리해 표기.

### P1-4 · 라이트 모드 경고 텍스트가 4.35:1 (미달)
`--warn: #9a6b00` on `--warnbg: #fdf6e3` = **4.35:1**. `.notice.warn`(.9rem/14.4px), `.chip.warn`(.85rem/13.6px), `.tag.flag`(.76rem/**12.16px**) 전부 본문 크기 → 4.5:1 필요. **미달.**
(다크는 `#d8b25e` on `#2a2418` = 7.66:1로 통과 — 두 테마의 품질이 다르다.)
덧붙여 `--warnbg: #fdf6e3`는 OKLCH **L=0.974 C=0.0261 H=90.1** — 이 팔레트에서 **유일하게 크림에 해당하는 표면**이다. 대비를 고치는 작업과 크림을 걷어내는 작업이 같은 한 번의 수정이다.

### P1-5 · 라이트 모드에는 카드 레이어가 존재하지 않는다
`--card #fff` vs `--bg #fbfbfa` = **1.035:1**. 카드 경계를 지탱하는 건 오직 `1px solid var(--line)` = **1.30:1**.
다크는 `#1e1f23` vs `#16171a` = **1.089:1**로 그나마 층이 보인다. 즉 **같은 마크업이 두 테마에서 다른 구조로 읽힌다.** product 레지스터가 요구하는 "패널용 두 번째 중립 레이어"가 라이트에서만 증발한다.

### P1-6 · 모든 인터랙티브 요소의 경계가 1.3:1 (WCAG 1.4.11 미달, 3:1 필요)
```css
textarea { border: 1px solid var(--line); }
button   { border: 1px solid var(--line); }
.tablewrap { border: 1px solid var(--line); }
```
| | line vs 배경 |
|---|---|
| 라이트 `#e2e2dd` vs `#fbfbfa` / `#fff` | **1.26 / 1.30:1** |
| 다크 `#2e3034` vs `#16171a` / `#1e1f23` | **1.36 / 1.25:1** |

붙여넣기 상자·버튼·표의 테두리가 저시력 사용자에게 사실상 없다. "붙여넣을 칸이 어디냐"가 화면의 첫 질문인데, 그 칸의 윤곽이 1.3:1이다.

### P1-7 · opacity로 만든 상태가 대비를 무너뜨린다
| 코드 | 실효 대비(라이트) | 판정 |
|---|---|---|
| `.card.done { opacity: .55 }` | 본문 **3.90:1**, muted **2.23:1** | 미달 — 게다가 안의 `textarea`는 **여전히 편집 가능** |
| `tr.absent td:not(:last-child) { opacity: .45 }` | **2.89:1** | 미달 — 학번·이름이라는 원자료가 3:1 아래로 |
| `<span style="opacity:.5">원문 없음</span>` | **3.27:1** | 미달 |
| `button:disabled { opacity: .4 }` (primary) | **1.84:1** | 규격상 면제이나, 탭 B 첫 화면의 유일한 주 버튼이 유령으로 보인다 |

`.card.done`은 "다 봤다"는 성취를 **정보를 흐리게 만들어** 표현한다. 검수를 끝낸 뒤 되돌아와 다시 읽는 동작이 벌을 받는다.

### P2-8 · 다크 중립이 보라 쪽으로 기울어 있다
`--bg #16171a` H=**271.1**, `--card #1e1f23` H=**274.6** (C≈0.006). 채도가 낮아 눈에 띄진 않지만, 반참조 목록 첫 줄이 "AI 챗봇 — 보라색"인 프로젝트에서 굳이 고를 색조는 아니다. impeccable의 "이유 없는 기본 틴트 금지"에도 걸린다. → accent(H≈158)나 채도 0 쪽으로.

### P2-9 · 통과한 것들 (기록)
본문 `--fg` on `--bg`: 라이트 **16.83:1**, 다크 **14.59:1**. `--muted` on `--bg`: 라이트 **5.18:1**, 다크 **6.33:1** — 질문하신 "muted 회색 본문"은 **양쪽 다 통과**한다. `--muted` on `--okbg`(태그) 라이트 **4.84:1**로 아슬하게 통과. `--bad` 계열은 라이트 5.82~6.57, 다크 6.35~6.95로 여유 있음.

## 3. 타이포그래피

### P0-10 · 오래 읽는 본문이 UI 라벨보다 작다 — 명시된 원칙의 역전
`PRODUCT.md`: "*세특 본문과 학생 원문은 오래 읽는 텍스트다. **본문 크기·행간을 UI 라벨보다 우선한다.***"

| 요소 | 크기 | 역할 |
|---|---|---|
| `.tabs button` | `.93rem` = **14.88px** | UI 라벨 |
| `.source` (학생 원문) | `.87rem` = **13.92px** | **오래 읽는 본문** |
| `textarea.prose` (세특) | **15px**/1.7 | **오래 읽는 본문** |
| `button` | `.9rem` = 14.4px | UI 라벨 |

학생이 쓴 글이 탭 라벨보다 **작다.** 화면의 존재 이유(원문↔세특 대조)를 담당하는 좌측 패널이 페이지에서 가장 작은 본문이다. 세특 15px도 40명을 연속 정독하기엔 부족하다.
→ 조치: 원문·세특 모두 16–17px / 행간 1.75 이상. 나머지 UI를 그 아래로 내려라. 순서를 뒤집는 것이지 전부 키우는 게 아니다.

### P0-11 · 한국어에 작동하지 않는 대문자 eyebrow — 금지 항목 정면 위반
```css
h2 { font-size: .78rem; text-transform: uppercase; letter-spacing: .08em; color: var(--muted); font-weight: 600; }
h3 { font-size: .74rem; text-transform: uppercase; letter-spacing: .07em; color: var(--muted); font-weight: 600; }
```
절대 금지 목록: "**Tiny uppercase tracked eyebrow above every section**". 정확히 이것이다 — 12.5px / 11.8px, 자간 확대, muted 색, **모든 섹션 위에**(`1 · 붙여넣기`, `2 · 확인`, `3 · 점수`, `4 · 저장`, `학생 원문`, `세특`).

여기에 한국어 특유의 악화 요인이 하나 더 붙는다. **`text-transform: uppercase`는 "붙여넣기"에 아무 효과가 없다.** 즉 이 선언은 라틴 타이포 관습을 한글에 그대로 복사한 것이고, 실제 효과는 **섹션 제목을 페이지에서 가장 작고 가장 흐린 글자로 만든 것뿐**이다. "지금 어디에 있는가"를 알려주는 글자가 12px muted다.

번호(`1 ·` `2 ·`)는 **실제 순서**(붙여넣기→확인→점수→저장)이므로 금지 조항의 예외에 해당한다 — 번호는 지켜도 된다. 문제는 조판이다.

### P1-12 · 스케일이 아니라 임의값 12종
`.74 / .76 / .78 / .8 / .85 / .87 / .88 / .9 / .93 / 1 / 1.3 rem` + `13px` + `15px` + `.88em`.
**0.19rem 구간 안에 9단계**가 몰려 있다. product 레지스터는 "고정 rem 스케일, 단계비 1.125–1.2"를 요구한다. 지금 인접 단계비는 1.01~1.03 — 사람 눈에 구분되지 않으면서 유지보수만 무겁다. 위계가 아니라 소음이다.
→ 조치: 13 / 14 / 16 / 18 / 20px 5단계로 압축.

### P1-13 · 줄 길이 — 가장 중요한 경고문이 가장 긴 줄
`main { max-width: 1180px; }` → `.privacy`, `.sub`, `.notice`가 최대 **약 1130px 폭**. 13.6px 한글 기준 **한 줄 약 83자**(권장 40–45자의 두 배). 하필 실명 유출 경고문이 이 폭이다.
`.split`(1fr 1fr, 각 ~575px)의 원문/세특은 약 38자로 **적정** — 정독 영역만 우연히 맞았다.
→ 조치: 산문 블록에 `max-width: 62ch` 별도 적용.

## 4. 레이아웃 · 세로 리듬

### P1-14 · 카드가 게으른 답으로 쓰였다 + 중첩
- 탭 A: 4개 단계가 **동일한 카드 4개**. 단계별 성격(입력 / 검증 / 선택 / 종결)이 시각적으로 구분되지 않는다.
- 탭 B: 학생 1명 = 카드 1개 → **40개의 동일 카드**. 목록으로서의 밀도는 product 레지스터가 허용하지만, 카드 껍데기가 아무 정보도 더하지 않는다.
- **중첩**: `.card`(테두리+반경 10) 안에 `.tablewrap`(테두리+반경 7) 안에 `table`(행마다 테두리). 탭 B는 `.card` 안에 `.source`(테두리+반경 7) + `textarea`(테두리+반경 7) + `.memo`(**점선** 테두리) — **한 카드 안에 경계 4겹.**
- 그런데 이 경계들이 전부 **1.3:1**(P1-6)이다. 복잡도는 다 치르고 신호는 얻지 못한다. **관공서 시스템 반참조에 가장 가까운 지점이 여기다** — 색이 아니라 경계 개수와 작은 활자 때문에.
→ 조치: 카드 껍데기를 걷고 여백과 활자로 구획. 표는 테두리 대신 행 간격과 정렬로.

### P1-15 · 세로 리듬의 기준 단위가 없다
`margin`/`padding` 실측: `.25 .4 .45 .5 .6 .7 .72 .8 .85 .9 1 1.15 1.2 1.5 2 rem` — **15종, 공배수 없음.** 눈에 보이는 증상은 "왜인지 정돈돼 보이지 않음"으로 나타난다. 문서의 질감은 배경색이 아니라 여기서 나온다(브랜드 성격이 명시한 바로 그 지점).
→ 조치: 4px(0.25rem) 배수 6단계로 고정.

## 5. 컴포넌트 상태

### P0-16 · 7개 상태 중 2개만 있다
```
:hover 0건 · :active 0건 · :focus-visible 0건 · transition 0건
```
(파일 전체 grep 결과다. 추정 아님.)

| 상태 | 존재 |
|---|---|
| default | O |
| hover | **X — 전 요소** |
| focus | 부분: `textarea:focus`만 |
| active | **X** |
| disabled | O (`opacity: .4`, 단 1.84:1) |
| loading | **X** — `saveFile()` await 중 시각 표시 없음 |
| error | 부분: `.notice.bad`는 있으나 필드 단위 오류 표시 없음 |

버튼에 hover가 없다 = 클릭 가능한지 마우스로 확인할 방법이 없다. `button`과 `.chip`이 둘 다 둥근 테두리 상자라 **정지 상태에서 구분되지 않는다.**

### P0-17 · 포커스 링 — 텍스트에어리어 하나뿐, 그것도 글자를 덮는다
```css
textarea:focus { outline: 2px solid var(--accent); outline-offset: -1px; }
```
- 이 한 줄이 파일의 유일한 포커스 스타일이다. **버튼·체크박스·`input[type=file]`·`.memo` 전부 브라우저 기본에 맡겨져 있다.** `--accent` 초록 버튼 위의 기본 링은 대비가 보장되지 않는다.
- `outline-offset: -1px` → 링이 상자 **안쪽**에 그려져 첫 줄 글자와 겹친다.
- `:focus`(마우스 클릭에도 발동)를 썼다. `:focus-visible` **0건**.
→ 조치: 전역 `:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }` + 다크에서 accent 대비 확인.

### P0-18 · 탭이 탭이 아니다 (ARIA 무효 + 키보드 미구현)
```html
<nav class="tabs">
  <button id="tab-a" aria-selected="true">명단과 점수</button>
```
`role=` **0건**, `tabindex` **0건**, `aria-label` **0건**.
`role="tab"` 없이 `aria-selected`만 쓰면 **스크린리더는 이 속성을 무시한다** — 유효하지 않은 ARIA다. `role="tablist"`, `aria-controls`, `role="tabpanel"`, `aria-labelledby` 전부 없다. 좌우 화살표 이동 없음.
`PRODUCT.md`: "*키보드만으로 붙여넣기 → 확인 → 저장, 그리고 검수 항목 간 이동이 가능해야 한다.*" — 탭 전환은 Tab+Enter로 겨우 되지만(네이티브 버튼 덕분), **검수 항목 간 이동은 40개 카드를 순차 Tab으로 훑는 것 외에 방법이 없다.** 항목 단위 이동(다음 학생 / 다음 우선검토)이 없다.

### P1-19 · 상태 변화가 스크린리더에 전달되지 않는다
`aria-live` **0건**. `#saved`("저장 중…", "저장했습니다"), `#rv-prog`("검수 12/40"), `#notices`, `#stats`, `#scorenotices` — 이 도구의 모든 피드백이 조용히 갱신된다. 특히 `#notices`는 **경고 전달 경로 그 자체**다.

### P1-20 · 네이티브 모달을 첫 수단으로 썼다 (product 금지)
```js
catch (err) { alert("검수번들.json을 읽지 못했습니다: " + err.message); }
...
if (notDone && !confirm(`검수 완료 표시가 없는 학생이 ${notDone}명 있습니다. 그래도 저장할까요?`)) return;
```
"Modal as first thought. Modals are usually laziness." 특히 `alert`은 **탭 B에서 가장 흔한 실패**(잘못된 파일 선택)의 유일한 응답이고, OS 대화상자 안의 영문 예외 메시지(`err.message`)를 교사에게 그대로 보여준다.

### P1-21 · 컴포넌트 어휘 불일치
- `<input type="file" id="rv-load">` — **탭 B의 시작 동작**인데 스타일이 전혀 없는 OS 위젯이 스타일된 버튼 옆에 놓인다. "동일한 폼 컨트롤 어휘" 위반.
- `.memo`만 `border: 1px dashed` — 다른 입력은 전부 solid. 점선은 새로 발명한 어포던스이며, 1.3:1에서 점선은 아예 안 보인다.
- `#rv-onlyflag` 토글의 유일한 상태 신호가 **라벨 글자 교체**("우선 검토만"↔"전체 보기"). `aria-pressed` 없음, 눌린 시각 상태 없음. 지금 필터가 걸려 있는지 라벨을 읽어 추론해야 한다.
- `.chip`과 `button`이 같은 형태 언어를 공유해 정보와 조작이 섞인다.

## 6. 빈 상태 — 화면이 아무것도 가르치지 않는다

### P0-22 · 탭 A 첫 화면: 4단계 중 3단계가 `hidden`
```html
<div class="card" id="result" hidden>   <!-- 2 · 확인 -->
<div class="card" id="scorecard" hidden> <!-- 3 · 점수 -->
<div class="card" id="savecard" hidden>  <!-- 4 · 저장 -->
```
처음 여는 사람이 보는 것: 제목 1줄 + 안내 1줄 + **빈 상자 1개.** 끝.
`PRODUCT.md` 설계 원칙 5: "*처음 여는 사람이 설명 없이 다음 칸을 안다. **화면 자체가 순서이고,** 붙여넣은 직후 결과가 보여야 다음 동작을 확신한다.*"
→ **화면이 순서일 수 없다. 순서의 3/4이 DOM에서 감춰져 있으므로.** 이 사람은 매뉴얼을 읽지 않는 사람이라고 문서가 못 박아 두었다.
→ 조치: 4단계를 처음부터 **비활성 상태로 보이게** 하라(연한 윤곽 + "붙여넣으면 여기에 표가 나타납니다"). 감추지 말고 잠가라.

### P0-23 · 탭 B 첫 화면: 완전한 공백
```html
<div id="rv-head"></div>
<div id="rv-list"></div>
```
파일 선택 버튼 하나, 비활성 저장 버튼 하나(1.84:1로 유령), 그리고 빈 공간. `검수번들.json`이 무엇인지, 어디서 생기는지, 불러오면 무슨 일이 벌어지는지 **화면이 한 글자도 말하지 않는다.** product 레지스터: "Empty states that **teach the interface**, not 'nothing here.'" — 지금은 'nothing here'조차 없다.
→ 조치: 불러오기 전 화면이 (a) 이 파일이 어느 단계에서 만들어지는지, (b) 불러오면 좌우 대조 화면이 된다는 것, (c) 저장 시 실명본과 diff 두 개가 나온다는 것을 미리 보여줘야 한다. 실물 형태의 골격(placeholder)이 최선이다.

### P1-24 · 오류 상태가 타이핑 중에 튄다
`document.getElementById("src").addEventListener("input", parse)` — 매 키 입력마다 전체 재파싱. 손으로 몇 글자 치는 순간 "**학번 열과 이름 열을 찾지 못했습니다**"라는 빨간 경고가 뜬다. 사용자가 아직 끝내지도 않은 입력에 대해 화면이 먼저 실패를 선언한다.

## 7. 모션

### P1-25 · 모션이 0이다. 그래서 상태 변화를 알릴 수단이 없다
```
transition 0 · animation 0 · @keyframes 0 · prefers-reduced-motion 0
```
product 레지스터는 "**150–250ms, 상태를 전달하는 모션**"을 요구한다. 장식 모션 금지는 지켰으나, **상태 전달 모션까지 없앤 것은 준수가 아니라 미구현**이다.

지금 각 상태 변화가 알려지는 방식:
| 사건 | 현재 |
|---|---|
| 붙여넣기 직후 결과 등장 | `result.hidden = false` — 카드 3개가 **한 프레임에 튀어나옴** |
| 저장 완료 | `<span>`에 글자가 갑자기 나타남 |
| 저장 진행 중 | 같은 `<span>`의 글자 교체뿐 |
| 검수 완료 체크 | `opacity: .55`로 **즉시 흐려짐**(전환 없음) |

붙여넣은 직후는 이 제품에서 **가장 중요한 순간**(원칙 5)인데, 아무 확인 신호 없이 레이아웃이 점프한다. 교사는 "된 건가?"를 스스로 판단해야 한다.
→ 조치: 최소 3곳만. (1) 결과 카드 등장 180ms fade+8px rise, (2) 저장 완료 문구 150ms fade-in + 지속, (3) `.done` 전환 200ms. `prefers-reduced-motion` 대체는 즉시 표시. 그 이상은 필요 없다.

## 10. 다음 단계에 넘기는 한 문장

색을 다시 고르는 작업이 아니다. **팔레트는 대체로 옳다(G1).** 고칠 것은 세 가지다 —
(1) 두 테마가 같은 토큰에서 반대 결과를 내는 지점(주 버튼·중복 행·경고색·카드 레이어)을 테마별로 검증된 쌍으로 바꾸고,
(2) 12종 활자와 15종 간격을 5×6 스케일로 압축해 "종이의 질감"을 조판에서 뽑아내고,
(3) 감춰 둔 단계를 드러내 화면이 실제로 순서가 되게 하는 것.
